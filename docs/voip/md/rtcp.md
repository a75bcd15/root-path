**Протокол RTCP**

**RTCP (RTP Control Protocol)** — это вспомогательный протокол управления, работающий в неразрывной связке с RTP. Его спецификация также описана в основном документе [**RFC 3550**](https://datatracker.ietf.org/doc/html/rfc3550). Если RTP доставляет звуковые пакеты, то RTCP — регулярно собирает статистику о доставке, выявляет проблемы на сети и помогает устройствам адаптироваться к изменяющимся условиям. RTCP работает поверх UDP. По стандарту RTCP всегда занимает следующий нечетный UDP-порт после согласованного четного порта RTP. Чтобы не забивать сеть служебной информацией, трафик RTCP строго лимитируется. Он должен занимать не более 5% от общей полосы пропускания, выделенной на весь медиапоток (RTP + RTCP). Обычно пакеты RTCP отправляются устройствами раз в 2–5 секунд.

RTCP-сообщения текстовыми не бывают — это строго бинарные пакеты. В одном UDP-кадре может быть упаковано сразу несколько типов сообщений (такие пакеты называют Compound Packets). Каждому типу пакета присвоен **свой идентификатор (Payload Type)**:

1. `SR` (Sender Report / Отчет отправителя, код 200): Отправляется активными участниками, которые в данный момент передают звук. Содержит абсолютное системное время (NTP timestamp), количество отправленных пакетов и байт. Помогает синхронизировать аудио и видео (например, в видеоконференциях).
2. `RR` (Receiver Report / Отчет получателя, код 201): Отправляется пассивными слушателями (или сервером АТС). Самый важный пакет для сетевого инженера. Содержит детальную статистику о качестве приема данных от противоположной стороны.
3. `SDES` (Source Description / Описание источника, код 202): Передает метаданные об участнике. Самое важное поле здесь — `CNAME` (Canonical Name), уникальный постоянный текстовый идентификатор пользователя, который не меняется, даже если во время звонка у устройства сменился `SSRC`.
4. `BYE` (Завершение, код 203): Извещает о том, что один из источников медиапотока покидает сессию (не путать с SIP BYE — RTCP BYE закрывает именно медиа-сессию).
5. `APP` (Приложение, код 204): Кастомные функции, определяемые разработчиками конкретного оборудования или ПО.

**Поля внутри Receiver Report**

При анализе качества звонка инженеры смотрят внутрь пакетов RTCP RR (Отчет получателя). Устройство вносит туда следующие критически важные метрики:

- **Fraction Lost** (Текущие потери): Процент пакетов, потерянных с момента отправки предыдущего отчета RTCP.
- **Cumulative Number of Packets Lost** (Общие потери): Суммарное количество потерянных пакетов за весь разговор.
- **Interarrival Jitter** (Джиттер): Среднее фазовое дрожание пакетов. Если это значение растет, значит, сетевые очереди на роутерах перегружены.
- **LSR** (Last SR Timestamp): Временная метка из последнего полученного отчета Sender Report.
- **DLSR** (Delay Since Last SR): Задержка между получением последнего SR и отправкой текущего отчета RR.

С помощью LSR и DLSR отправляющая сторона вычисляет точное круговое время задержки пакета в сети — RTT (Round Trip Time), то есть пинг между устройствами на уровне медиаданных.

# Схема работы RTCP в процессе разговора

Пока абоненты общаются, оборудование циклично обменивается отчетами:

```
    Телефон А (Говорит)                                   Телефон Б (Слушает)
    [RTP Порт: 10002]                                     [RTP Порт: 10004]
    [RTCP Порт: 10003]                                    [RTCP Порт: 10005]

             |                                                     |
             |============ RTP Поток (Звук идет) =================>| (Каждые 20 мс)
             |                                                     |
             |-- RTCP SR (Код 200: "Я отправил 250 пакетов") ----->| (Раз в 3 сек)
             |                                                     |
             |<-- RTCP RR (Код 201: "Я принял всё. Потери: 0%,") --| (Б сообщает о
             |            "Джиттер: 4мс, RTT: 15мс")               | качестве сети)
             |                                                     |
             |                             (В сети начались лаги)  |
             |                                                     |
             |============ RTP Поток (Пакеты теряются) ===========>|
             |                                                     |
             |<-- RTCP RR (Код 201: "Внимание! Потери: 12%,") -----| (Сигнал тревоги:
                          "Джиттер вырос до 54мс!")                | АТС или телефон
                                                                   | могут снизить 
                                                                   | битрейт кодека)
```

Таким образом достигается:

1. Адаптация кодеков (WebRTC / Opus): Если в RTCP RR зафиксирован рост потерь пакетов и джиттера, современный кодек (например, Opus) мгновенно снизит битрейт и включит алгоритм FEC (Forward Error Correction) для компенсации потерь.
2. Диагностика и СLA: Системы мониторинга АТС парсят RTCP-пакеты, чтобы рисовать графики качества связи и выставлять оценку MOS для каждого звонка без необходимости слушать саму запись.
