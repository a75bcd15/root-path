**Протокол SDP**

**SDP (Session Description Protocol)** — это протокол описания сессии. Его главный стандарт регламентируется документом [**RFC 4566**](https://datatracker.ietf.org/doc/html/rfc4566).

SDP является декларативным языком описания параметров связи. В IP-телефонии он почти всегда находится внутри тела (`Message Body`) SIP-запросов, а заголовок SIP `Content-Type` при этом принимает значение `application/sdp`.

SDP-текст состоит из строк вида `<тип>=<значение>`, где `<тип>` — это всегда одна латинская буква, а регистр имеет строгое значение. Внутри блока строки должны идти в строго определенном порядке.
Все параметры делятся на три уровня: описание сессии (общие данные), описание времени и описание медиапотока (звук или видео).

**Пример SDP-блока внутри SIP-пакета:**

```
v=0
o=IP-Phone 289472 289472 IN IP4 192.168.1.50
s=VoIP-Call
c=IN IP4 192.168.1.50
t=0 0
m=audio 40002 RTP/AVP 8 0 101
a=rtpmap:8 PCMA/8000
a=rtpmap:0 PCMU/8000
a=rtpmap:101 telephone-event/8000
a=fmtp:101 0-15
a=sendrecv
```

**1. Описание сессии (Session Level)**

- `v=` (Protocol Version): Версия SDP. На данный момент всегда равна 0.
- `o=` (Owner/Creator): Инициатор сессии и уникальный идентификатор. Синтаксис: `o=<имя_пользователя> <id_сессии> <версия_сессии> <тип_сети> <тип_адреса> <IP_адрес>`
- `s=` (Session Name): Имя сессии. Если имя не задано, обычно пишут просто `s=-` или `s=VoIP-Call`.
- `c=` (Connection Information): Указывает сетевой адрес, на который удаленная сторона должна отправлять медиатрафик (RTP). Именно здесь кроется проблема «односторонней слышимости», если в поле `c=` из-за NAT попадает серый локальный IP-адрес вместо белого.

**2. Описание времени (Time Level)**

- `t=` (Timing): Время начала и окончания сессии. Для обычных телефонных звонков, которые создаются «здесь и сейчас» и длятся неопределенно, всегда устанавливается в `t=0 0`.

**3. Описание медиапотока (Media Level)**

- `m=` (Media Descriptions): Ключевое поле, объявляющее тип трафика и порты. Синтаксис: `m=<тип_медиа> <порт> <протокол> <форматы/кодеки>`. Примечание: `8 0 101` — список поддерживаемых кодеков в порядке приоритета (`8` — это G.711a, `0` — G.711u, `101` — DTMF-сигналы).
- `a=` (Attributes): Дополнительные свойства (атрибуты), расширяющие поле `m=`. Синтаксис: `a=rtpmap:<код> <кодек>/<частота>` — расшифровка кодеков. 

# Модель Offer/Answer (Предложение / Ответ)

Обмен SDP-данными между АТС и телефонами строго следует модели **Offer/Answer** [**(RFC 3264)**](https://datatracker.ietf.org/doc/html/rfc3264). Собеседники должны прийти к консенсусу (согласовать общий кодек и порты).

1. Offer (Предложение): Вызывающая сторона (А) отправляет `INVITE` со своим списком кодеков.
2. Answer (Ответ): Вызываемая сторона (Б) в пакете `200 OK` присылает свой встречный SDP, выбирая то, что она тоже поддерживает.

После этого обмена обе стороны точно знают, куда слать RTP-пакеты и с помощью какого алгоритма их кодировать/декодировать.
