**Протокол RTP**

**RTP (Real-time Transport Protocol)** — это специализированный сетевой протокол прикладного уровня, предназначенный для передачи аудио и видео в реальном времени. Его спецификация описана в документе [**RFC 3550**](https://datatracker.ietf.org/doc/html/rfc3550). 

RTP работает строго поверх UDP. В реальном времени нет смысла использовать TCP: если пакет с кусочком звука потерялся, его повторная отправка займет слишком много времени и долетит до уха уже невпопад. Проще этот пакет проигнорировать (джиттер-буфер сгладит потерю). RTP использует динамические четные UDP-порты (обычно из диапазона 10000–20000 или 16384–32768). Конкретный номер порта согласовывается индивидуально для каждого звонка на этапе обмена SDP-заголовками. Каждая RTP-сессия сопровождается контрольным **протоколом RTCP (RTP Control Protocol)**. RTCP использует следующий нечетный порт (например, если RTP идет по порту 40002, то RTCP займет порт 40003). Он не передает голос, а собирает статистику о качестве связи: потерях пакетов, джиттере и задержках (RTT).

**Структура и заголовки пакета RTP**

RTP-пакет инкапсулируется внутрь UDP-датаграммы. Минимальный размер фиксированного заголовка RTP составляет 12 байт.

1. `V` (Version, 2 бита): Версия протокола. В современном VoIP всегда равна 2.
2. `P` (Padding, 1 бит): Флаг выравнивания. Если установлен, в конце пакета добавлены пустые байты для дополнения до нужного размера блока (например, при шифровании).
3. `X` (Extension, 1 бит): Флаг расширения. Показывает, присутствуют ли за фиксированным заголовком дополнительные кастомные заголовки.
4. `CC` (CSRC Count, 4 бита): Количество идентификаторов CSRC (используется, если звук идет от микшера, объединяющего несколько источников в конференцию). Для обычного звонка равно 0.
5. `M` (Marker, 1 бит): Маркер. Имеет значение для конкретного профиля трафика. В телефонии часто отмечает первый пакет аудио после паузы/тишины (при включенном механизме подавления тишины VAD).
6. `PT` (Payload Type, 7 бит): Тип полезной нагрузки. Указывает, какой именно кодек использован для сжатия голоса в данном пакете. Примеры фиксированных кодов: 0 — G.711 u-law (PCMU), 8 — G.711 a-law (PCMA), 18 — G.729. Динамические кодеки (например, Opus) используют значения из диапазона 96–127, которые предварительно описываются в SDP.
7. `Sequence Number` (Порядковый номер, 16 бит): Инкрементируется (увеличивается на 1) с каждым отправленным пакетом. Стартовое число выбирается случайно.
8. `Timestamp` (Временная метка, 32 бита): Отражает момент времени, в который был сделан первый замер звука, вошедший в этот пакет. Стартовое значение тоже выбирается случайно. Шаг временной метки привязан к частоте дискретизации кодека. Например, для кодека G.711 (8000 Гц) при отправке пакетов каждые 20 мс (0.02 секунды), Timestamp каждого следующего пакета будет увеличиваться ровно на: 8000 × 0.02 = 160 единиц. Это помогает джиттер-буферу воспроизводить звук плавно, без рывков, рассчитывая точные интервалы между пакетами, независимо от сетевых задержек.
9. `SSRC` (Synchronization Source, 32 бита): Уникальный случайный идентификатор источника синхронизации (конкретного устройства/микрофона в текущей сессии). Помогает отличить один медиапоток от другого в рамках одного сетевого соединения (например, если на один порт прилетает трафик от двух участников конференции).

# Схема 1: Классический двусторонний звонок (P2P / Point-to-Point)

После согласования сессии через АТС (по протоколу SIP), телефоны часто отправляют RTP-трафик напрямую друг другу, минуя сервер, чтобы снизить на него нагрузку (если это не запрещено настройками АТС или NAT).

```
    Телефон А (192.168.1.50)                           Телефон Б (192.168.2.30)
      [RTP Порт: 14002]                                  [RTP Порт: 18006]

             |                                                  |
             |======== RTP Поток (Кодек G.711a, PT=8) =========>| (А шлет на Б:18006)
             |        Seq=1001, Timestamp=160                   |
             |        Seq=1002, Timestamp=320                   |
             |                                                  |
             |<======= RTP Поток (Кодек G.711a, PT=8) ==========| (Б шлет на А:14002)
             |        Seq=5504, Timestamp=160                   |
             |        Seq=5505, Timestamp=320                   |
             |                                                  |
             | - - - - RTCP Статистика (каждые ~5 сек) - - - - >| (Порт 14003 -> 18007)
             |< - - - - RTCP Статистика (каждые ~5 сек) - - - - | (Порт 18007 -> 14003)
```

# Схема 2: Звонок через АТС (Proxy Mode / Запись разговора)

Если на АТС включена запись разговоров, перевод вызова или участники находятся за жестким NAT, медиапоток идет строго через сервер телефонии, который выступает в роли ретранслятора (B2BUA).

```
    Телефон А                         Сервер (АТС)                         Телефон Б

        |                                  |                                  |
        |==== RTP (Порт А -> Порт АТС1) ===>|                                  |
        |                                  |==== RTP (Порт АТС2 -> Порт Б) ===>|
        |                                  |   [Запись и склейка аудио файлов] |
        |                                  |<=== RTP (Порт Б -> Порт АТС2) ====|
        |<=== RTP (Порт АТС1 -> Порт А) ===|                                  |

```
